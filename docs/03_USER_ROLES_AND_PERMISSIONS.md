# Роли и права доступа

## Роли

| Роль | Назначение |
|---|---|
| `CLIENT` | Клиент автомойки, работает через Telegram Mini App. |
| `ADMIN` | Администратор организации, управляет операционной частью. |
| `OWNER` | Владелец организации, управляет организацией, филиалами и администраторами. |

Другие роли не создаются.

## Правила доступа CLIENT

`CLIENT` может обращаться только к client endpoint'ам. Backend должен проверять:

- Telegram authentication payload;
- существование customer по `telegram_user_id`;
- принадлежность автомобиля клиенту;
- принадлежность записи клиенту;
- принадлежность отзыва завершенной записи клиента.

`CLIENT` не должен иметь доступ к `Admin API` даже при попытке прямого HTTP-запроса.

Для автомобилей `CLIENT` может выполнять CRUD только над объектами, где `car.owner_id = auth.user_id`.

Для услуг и филиалов `CLIENT` видит только активные объекты своей `organization_id`.

Stage 6 booking permissions:

- `CLIENT` может создать запись только для себя через `POST /api/bookings/`.
- `CLIENT` не передает `client_id`, `organization_id`, `workstation_id`, `end_at`, `status`, `price`.
- `CLIENT` видит только свои записи через `/api/my-bookings/`.
- `CLIENT` может отменить свою запись только в статусе `PENDING`.
- `ADMIN` и `OWNER` видят записи только своей организации через `/api/admin/bookings/`.
- `ADMIN` и `OWNER` на Stage 6 могут менять только `status` и `admin_comment`.

## Правила доступа ADMIN

`ADMIN` работает только в рамках своей `organization_id`.

Backend должен проверять:

- административную аутентификацию;
- роль `ADMIN` или выше;
- принадлежность объекта организации администратора;
- принадлежность филиала этой организации;
- отсутствие попытки доступа к другой организации через IDOR.

`ADMIN` не может управлять администраторами, филиалами и настройками организации.

`ADMIN` может управлять услугами, боксами, рабочими часами и исключениями расписания только в пределах своей организации.

## Правила доступа OWNER

`OWNER` имеет полный доступ внутри своей организации, но не имеет доступа к другим организациям.

Backend должен проверять:

- административную аутентификацию;
- роль `OWNER`;
- `organization_id` в auth context;
- принадлежность всех изменяемых объектов этой организации.

## Серверный auth context

После аутентификации backend формирует auth context:

```text
actor_id
actor_type: client | admin_user
role: CLIENT | ADMIN | OWNER
organization_id
customer_id nullable
admin_user_id nullable
telegram_user_id nullable
```

Все защищенные сервисы получают `organization_id` из этого context, а не из произвольного тела запроса.
